# cccalendar 版本跨越方案

> 范围：仅整理前面指定的第 2、3、4、5、7 项。会议室名称的单字符模糊匹配已经完成，不作为本方案的后续待办。
>
> 执行约束：所有代码切片继续遵循 Red → Green → Refactor → Verify；每个切片完成后立即更新 `WORKLIST.md`。本方案是路线图，不代表所有条目已经实现。

## 现状基线

- 客户端是本地优先的 .NET/WPF 应用，核心数据保存在 SQLite。
- 团队会议室和预约已经具备 ASP.NET Core API、SignalR 通知、游标增量接口、幂等键、PostgreSQL 存储和阿里云部署能力。
- 当前云端仍保留 DevToken/HTTP 过渡配置；正式长期使用需要 HTTPS、OIDC 和更严格的凭据生命周期。
- AI 助手已经具备受控只读工具、提案确认、撤销、上下文和失败恢复；后续重点是可靠性、权限边界和可诊断性。
- 发布流程已经能生成 Windows 安装包并上传 OSS，但签名、灰度、自动回滚和数据库迁移闸门仍需补强。

## 2. 增量同步与离线恢复

### 目标

让多台电脑在网络抖动、进程重启或短暂离线后，能够可靠地补齐变化，不重复应用，也不丢失本地数据。

### 关键设计

`cursor` 是客户端已经成功应用的服务端变更序号。客户端收到 SignalR 通知后，以本地 cursor 请求 `/api/workspaces/{workspaceId}/sync?cursor=...`；服务端返回 cursor 之后的变更，客户端全部应用成功后才推进本地 cursor。cursor 不是时间戳，也不是权限凭据。

- 变更按工作区单调递增，响应携带 `nextCursor`、是否还有下一页和变更版本。
- 应用变更与保存 cursor 必须保持“先应用、后推进”；中途失败时保留旧 cursor，重试不会跳过数据。
- 当服务端发现 cursor 过旧或变更日志已压缩，返回“需要全量快照”；客户端先保存本地未提交数据，再下载快照并重新建立 cursor。
- 本地 Outbox 记录待提交命令、幂等键、重试次数和最后错误；网络恢复后按顺序重试，成功后再移除。
- UI 明确显示在线、同步中、离线、冲突和需要重新同步，不用静默的旧数据冒充在线状态。

### 分阶段交付

1. P41：补充分页、重复通知、进程重启和应用失败不推进 cursor 的测试。
2. P42：实现 cursor 过期的全量快照协议，以及 Outbox 的持久化重试和退避。
3. P43：在两台独立客户端进行断网、恢复、同时编辑和重复提交验收。

### 验收标准

- 同一变更最多被本地应用一次，应用失败可以从原 cursor 重试。
- 客户端强制退出后重启，能够继续同步而不重复创建预约。
- 断网期间个人日程仍可用；恢复网络后团队预约最终收敛。
- cursor 过期时不会显示“同步成功”，而是进入可操作的全量恢复状态。

## 3. 云端数据一致性与多人冲突

### 目标

把会议室预约从“接口可用”提升为可长期运行的事务系统，并为未来同步个人日程、待办和项目保留清晰边界。

### 关键设计

- PostgreSQL 作为生产唯一事实源，房间、成员、预约、变更日志和幂等记录使用事务写入。
- 预约继续使用半开区间 `[start, end)`，冲突由数据库约束和服务端事务双重保证，不能只依赖客户端预检查。
- 创建、修改、删除命令都带幂等键；重复请求返回第一次结果，不产生第二条预约。
- 修改使用对象版本或 `If-Match`，版本不一致返回 409，并返回当前对象摘要，禁止静默覆盖他人修改。
- 软删除、变更日志和审计记录保留操作者、时间、工作区和对象版本；数据清理必须有保留期和备份策略。
- 数据库迁移采用向前兼容：先加字段/表，再切换读写，最后清理旧字段；每次迁移必须有回滚或恢复说明。

### 分阶段交付

1. P44：补充修改版本冲突、重复删除、幂等重放和事务回滚测试。
2. P45：完善 PostgreSQL 迁移锁、备份恢复演练和变更日志保留策略。
3. P46：把个人日程同步限定为独立切片，先完成只读镜像，再评估双向编辑，避免一次扩大冲突面。

### 验收标准

- 两台客户端同时预约同一时段时，只有一个事务成功，另一个收到可解释的 409。
- 网络超时重试不会产生重复预约；服务端重启后数据、幂等键和游标仍然存在。
- 迁移失败不会破坏旧版本读取；备份可以在新实例恢复并通过健康检查。

## 4. 安全、身份与权限

### 目标

从阿里云上的过渡性共享口令，升级为可审计、可撤销、最小权限的团队身份体系。

### 关键设计

- 对外只提供 HTTPS/443，ASP.NET Core 仅监听反向代理后的内部端口；数据库端口不对客户端开放。
- 生产登录使用 OIDC + PKCE，access token 短时有效，refresh token 只存 Windows 凭据管理器，并支持撤销和轮换。
- DevToken 仅保留在开发/验收环境，生产配置启动时拒绝启用；共享口令不写日志、不进入普通 JSON 配置。
- 服务端按工作区校验 `sub`、成员关系和角色：Viewer 只读，Member 可预约，Admin/Owner 管理房间和成员。
- 所有写操作记录审计事件，但不记录令牌、密码、完整 AI 提示词或附件正文；日志中的用户输入和 URL 必须脱敏。
- 增加登录失败限流、口令轮换、成员禁用和会话撤销流程，并在客户端明确显示身份过期状态。

### 分阶段交付

1. P47：域名、反向代理、Let's Encrypt 证书和 `RequireHttps` 生产配置验收。
2. P48：真实 OIDC 多成员登录、角色矩阵、令牌刷新/撤销和禁用成员测试。
3. P49：关闭生产 DevToken，完成密钥轮换、审计检索和安全演练。

### 验收标准

- HTTP 请求自动跳转或被拒绝，客户端只连接 HTTPS/443。
- Viewer 无法创建、修改或删除预约；跨工作区对象访问统一返回 403/404。
- 令牌过期可无感刷新，撤销后立即失效；服务器日志和备份中不存在明文密钥。

## 5. AI 助手可靠性与可控扩展

### 目标

让 AI 从“能调用工具”提升为可审计的日历工作流入口，同时保持本地优先、用户确认和最小权限边界。

### 关键设计

- 工具按只读查询、草案生成、确认写入三层分组；模型永远不能绕过确认直接写入或删除。
- 请求上下文包含当前用户、工作区、时区、日期范围和来源标识；服务端/本地工具再次校验权限，不能信任模型传入的 ID。
- 所有写入先生成结构化提案，展示标题、时间、地点、参与人、冲突和副作用；确认后使用幂等键执行。
- 对附件、外部链接和会议邀请采用大小、类型、字段和出网策略校验；失败时保留输入并给出可重试原因。
- Provider 适配层统一处理超时、取消、流式断线、空响应、工具轮次和限流；错误信息区分用户可修复问题与服务端故障。
- 增加工具调用追踪 ID、耗时、结果数量和 token/字节统计，默认脱敏；用户可删除 AI 历史并选择不持久化本轮会话。
- 后续再评估摘要、检索和模型路由；在没有评测集和权限隔离前，不引入自动执行 agent 或无边界向量检索。

### 分阶段交付

1. P50：建立固定的日程查询、冲突、提案确认和拒绝评测集，纳入 CI 回归。
2. P51：统一 Provider 超时/取消/限流和工具追踪，补充断线重试与历史损坏恢复测试。
3. P52：增加可选摘要和本地检索，明确数据范围、删除策略和离线行为后再灰度。

### 验收标准

- 同一输入在固定评测集上的结构化字段和安全拒绝结果稳定，不因 Provider 切换而越权。
- 任意写操作都能追溯到用户确认、幂等键和审计事件；取消或失败不会产生半条数据。
- AI 不可读取未授权工作区、密钥、完整数据库或未明确允许的附件正文。

## 7. 工程质量、可观测性与发布体系

### 目标

让每个版本都可验证、可追踪、可回滚，降低云端升级和桌面自动更新的风险。

### 关键设计

- CI 固定执行格式检查、构建、全量测试、覆盖率、迁移验证、发布启动冒烟和安装器编译；失败禁止生成可发布清单。
- 每个功能切片必须有 Red/Green/Refactor/Verify 记录和唯一下一步；跨模块改动增加 API、数据库和运行时验收。
- Server 提供匿名 `/health` 和受保护的诊断信息；结构化日志包含 request ID、workspace、user、cursor、幂等键和耗时，但不含秘密。
- 增加基础指标：请求成功率、409 冲突率、同步延迟、cursor 落后量、Outbox 重试、数据库连接和磁盘空间；关键阈值告警到运维渠道。
- 更新清单使用 HTTPS、SHA-256 和代码签名；客户端下载前校验版本、签名和哈希，安装失败保留旧版本并支持回滚。
- 发布采用灰度顺序：测试环境 → 内部客户端 → 少量团队 → 全量；数据库迁移与客户端最低兼容版本写入发布说明。
- 阿里云升级前自动备份 `/root/cccalendar/data` 或 PostgreSQL，升级后验证 `/health`、房间目录、预约查询和同步接口，再清理旧包。

### 分阶段交付

1. P53：统一 CI/发布闸门、结构化日志和基础健康指标。
2. P54：完成安装包代码签名、灰度通道、失败回滚和数据库迁移兼容矩阵。
3. P55：建立阿里云告警、备份恢复演练和季度升级演练记录。

### 验收标准

- 任一发布产物都能关联源码版本、测试结果、安装包哈希和发布人。
- Server 升级失败时旧进程或旧版本可恢复，数据和预约不丢失。
- 发生同步、认证或预约异常时，可以仅凭 request ID、指标和脱敏日志定位问题。

## 推荐实施顺序

1. 先完成 P41–P43，稳固同步和离线恢复；这是多人共享体验的基础。
2. 再完成 P44–P46，确保 PostgreSQL 事务、版本冲突和备份恢复可靠。
3. 并行推进 P47–P49，把公网 DevToken 过渡到 HTTPS/OIDC。
4. 在安全边界稳定后推进 P50–P52，避免 AI 功能放大数据和权限问题。
5. 最后以 P53–P55 固化 CI、可观测性、签名发布和云端演练，形成 1.0 的发布门槛。

- `0.8.x`：PostgreSQL 迁移/备份、版本冲突和 HTTPS/OIDC 完成生产验收。
- `0.9.x`：AI 评测集、工具追踪和失败恢复纳入持续集成。
- `1.0.0`：签名安装、灰度/回滚、告警和恢复演练完成，才承诺长期团队使用。
